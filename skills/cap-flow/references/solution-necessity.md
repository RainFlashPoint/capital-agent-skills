# 方案必要性 Gate

这个 Gate 防止把“需要在新条件下重新验证”误解成“需要重新实现一套方案”。当任务涉及迁移、换地址、换凭据、升级、加固、适配新环境，或仓库里已经存在成功路径时，在计划和实现前执行；普通新增功能只需确认没有可复用基线，不必制造额外文档负担。

## 判断顺序

1. **既有成功路径**：定位当前实际工作的入口、构建/测试/发布链路及最近成功证据；说明哪些部分可以原样复用。没有证据时写 `unknown`，不能把“没调查到”当成“必须重建”。
2. **必要差异**：把用户要求的新结果与既有路径逐项比较，只列为了达到新结果必须变化的地址、凭据引用、配置、接口或行为。
3. **最小方案**：先保持实现不变，在新目标上替换必要差异并重新取证。新环境需要新证据，但**重新取证 ≠ 重新实现**。
4. **扩张证明**：若要改动必要差异之外的核心路径，逐项给出原始需求引用或已观察失败证据，并说明为什么现有路径无法满足、较小改法为何不成立、扩张后要新增什么验证。

以下改动默认属于“核心路径扩张”：更换构建工具或构建链路、基础镜像、源码导出/过滤策略、依赖安装方式、产物布局、执行拓扑、配置打包方式，以及新增通用隔离/发布框架。假设性的安全顾虑、个人偏好、顺手重构或“新地址尚未验收”本身都不是扩张证据。

## 产物契约

在 `task-context.md` 记录：

```markdown
## Solution necessity
- existing-success-path: <路径/符号/命令/最近成功证据；没有则 unknown + 已查来源>
- required-delta: <用户目标相对现状的必要差异；没有写 none>
- preserve: <必须保持不变并复用的实现或契约>
- proposed-expansions: none | <扩张项 → 原始需求或失败证据 → 较小方案为何不成立>
- revalidation: <在新目标上如何重新取证>
- invalidates-on: <何种新失败或需求变化要求重算>
```

计划中的每个任务必须能映射到 `required-delta`、必要验证或有证据的扩张项；映射不到的任务先删除或回到需求澄清。执行中首次出现计划外核心路径改动时，暂停该改动并刷新本段，不能用实现过程中补写的 spec/plan 反向证明它原本必要。

## 评审判据

评审先用用户原始意图、任务侦察证据和 `Solution necessity` 审方向，再审局部代码是否正确。spec、plan 和 diff 都是被审对象，不是扩张授权来源：即使新增框架测试全绿，只要无法证明它是必要差异，仍属于 scope drift。反之，保留旧实现并在新地址重新跑出的新证据，是有效迁移验收，不应因“代码没重写”被判未完成。
